# 修改归属

先读取实时 stack 和相关 PR 的标题、描述及净变化，再判断修改所属层。不要仅根据当前 checkout、
文件路径或 PR 编号归类。

## 修改现有层

满足任一情况时，优先修改已有功能层：

- 修复该层引入的缺陷或遗漏。
- 补充同一功能的测试、翻译、文档或防回归检查。
- 修改仍由该 PR 当前表达的维护目的完整解释。
- 文件跨越多个模块，但修改原因仍属于同一个功能。

治理、CI 或维护文档也按其目的归入已有治理层；通过实时 PR 内容定位，不硬编码编号。

## 创建新层

满足任一情况时创建新的功能 PR：

- 新增独立的用户需求或维护责任。
- 放进已有 PR 后，其标题或描述将无法准确解释净变化。
- 将来需要单独撤销、替换或长期维护这段历史。

新层可以完全依赖前一层。不要为了让 PR 独立运行而复制代码或引入兼容层。

## 边界不清时

根据“为什么修改”和将来的维护边界做最小合理判断，并向用户说明。只有不同选择会实质改变
历史结构或产品含义时才请求用户决定；其它实现细节继续推进。
