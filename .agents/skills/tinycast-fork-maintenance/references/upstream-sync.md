# 同步上游

同步不是单纯消除 Git 分叉，而是把每个 fork 功能层重新应用到最新上游，并确认它的目的、覆盖面和
验证仍然成立。多数同步可以直接级联 rebase；是否需要额外修改由本次上游增量和各层职责动态决定。

同步前读取 [stacked-pr.md](stacked-pr.md)，获取远端实时 stack，并明确本次授权是否包含历史改写、
推送和 PR 更新。未授权写入时只调查、演练和报告，不改变正式分支或远端。

## 建立同步基线

1. 确认工作树没有会被切分支或 rebase 干扰的用户改动。
2. Fetch `origin` 和 `fork`，记录 `origin/main`、`fork/main`、各层 head 和 PR base/head。
3. 验证 `fork/main` 没有 fork 专属提交，并判断它相对 `origin/main` 是相同、可快进还是已经分叉。
   `main` 只能快进到上游；若已分叉则停止，不用 rebase 或 force-push 掩盖异常。
4. 以旧 `fork/main..origin/main` 为上游增量，阅读提交主题、变更路径和高影响 diff。不要只看提交数
   或依赖 `gh stack view` 的 `needsRebase`：在 `fork/main` 尚未更新时，它可能仍把旧 trunk 视为正常。

先区分上游增量中的功能、重构、删除、生成文件、构建测试、文档和仓库治理变化。重点找出与 fork
各功能层相同的文件、符号、界面和对外契约，以及上游是否已经部分或完整吸收某层目的。

## 规划每个功能层

从 stack 底部到顶部读取每层 PR 的目的和该层相对直接 base 的净变化，然后把它与上游增量比较。
为每层选择实际需要的处理：

- 没有语义交集：直接 rebase，之后验证净变化未漂移。
- 同一区域有重构、改名或新增入口：rebase 后按该层原有目的适配新结构；不要为保留旧 patch 恢复
  已被上游替换的架构或 API。
- 上游扩大了该层应覆盖的产品表面：在这一层补齐覆盖，而不是仅解决文本冲突。
- 上游已实现同一目的：比较行为和净变化，再决定删掉重复提交、缩小或折叠该层。结构调整按
  [stacked-pr.md](stacked-pr.md) 执行，不自动关闭或删除 PR。
- 无法从现有 PR 目的判断某项上游变化是否应纳入：保留为显式待决项，不擅自扩大功能范围。

审计维度随功能层而定，包括但不限于用户可见 UI、数据或设置契约、持久化、权限、并发边界、测试、
生成物和文档。冲突只是发现语义交集的一种信号；无冲突不表示该层仍然完整。

本地化层还要检查上游新增或改名的设置、按钮、菜单、对话框、HUD、占位符、帮助与无障碍文本，
以及运行时拼接的可见字符串。确认新表面采用该层既有的 key/默认值约定、String Catalog 有完整翻译，
并让本地化 lint 和相关 harness 覆盖它；不要把这份清单套到不负责本地化的层。

审计本地化时不要只搜索 `Text("…")` 等直接字面量。上游重构很容易让同一段文字跨过自动提取边界；
逐项检查：

- 先存入 `String`、模型属性或枚举属性，再交给 view 的标题和说明。
- 通过自定义 view 参数、菜单数据、搜索占位符、无障碍属性或 presenter 间接呈现的文字。
- 条件标题、字符串拼接、插值、数量和格式化参数；运行时 key 必须与 catalog key 和占位符签名一致。
- view 或组件改名、移动、抽取后，原来命中 `LocalizedStringKey` 的调用是否变成普通 `String` 重载。
- 为适配新增的本地化 helper 是否仍由正确 feature 拥有；不要为了复用破坏模块隔离或把 feature 细节
  提升到共享设计系统。

静态 lint 只能证明它覆盖的模式。还要直接阅读上游增量中新建或重写的 UI、模型到 UI 的文字路径，
并从最终安装包回读语言资源、验收代表性的动态和间接呈现文本。

## 执行与复核

在用户授权范围内，先快进本地 `main` 并更新 `fork/main`，使 fork trunk 与 `origin/main` 相同；随后
从 stack 底部到 `integration/current` 级联 rebase。通常使用 `gh stack rebase --remote fork`；需要
预判冲突或尚未获准改写正式分支时，在临时 clone 或临时分支中按相同 base 顺序演练。

解决冲突时先确认上游改动意图，再把当前功能层的目的移植到新结构。不要机械选择 ours/theirs，也
不要顺手把更高层职责塞进当前层。每完成一层都检查：

- 该层相对新直接 base 的净变化仍只表达本 PR 的目的。
- 原有提交没有被意外丢失、重复应用或混入上游内容。
- 上游新增表面需要的适配已放在职责正确的层；文档和测试仍与行为一致。

完成整个 stack 后运行项目验证。需要本地验收时，再读取 [dev-app.md](dev-app.md) 安装完整集成版本。
验证通过且用户授权推送后，使用 `gh stack push --remote fork` 统一推送，避免先推底层造成上层 PR
短暂错位；然后重新读取所有 PR 的 base/head、检查、mergeability 和 stack 线性关系，并确认
`integration/current` 仍是顶部及 fork 默认分支。

同步报告区分：上游增量、纯 rebase 的层、发生语义适配的层、尚待决定的职责变化、验证结果和未获
授权的远端动作。不要因为同步上游而自动合并、关闭或删除功能 PR。
